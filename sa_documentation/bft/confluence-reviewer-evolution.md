## 1. Замысел: какую боль лечим

**Контекст.** Группа системных аналитиков пишет требования в корпоративном Confluence.
Руководитель группы обязан контролировать качество этих документов: соответствие
внутреннему шаблону (есть ли все обязательные разделы) и качество наполнения (полны ли
требования, нет ли противоречий, поймёт ли их разработчик). Сегодня этот контроль —
ручной, несистемный и дорогой: документов сотни, проверяются они по наитию,
обратная связь до аналитика доходит не всегда.

**Ценностное предложение сервиса** (из БФТ CR-001):

1. **Автоматический контроль по двум независимым факторам** — соответствие шаблону
   (скриптовая проверка структуры) и качество наполнения (оценка ИИ: полнота,
   непротиворечивость, понятность).
2. **Обратная связь доходит до автора**: итоги проверки отправляются комментарием
   прямо на Confluence-страницу — механика ФТ-CR-17 (отправка комментария на страницу
   из UI; текст комментария может быть и произвольным текстом руководителя, ПТ-CR-5).
3. **Экономия времени руководителя**: вместо чтения каждого документа — работа
   с исключениями (что не прошло и почему).
4. **Приватная память руководителя**: заметки по документам, не видимые аналитикам.

**Ограничения и отправные решения.** Стек Python + React задан заказчиком. В качестве
ИИ взят GLM (General Language Model — семейство моделей Zhipu AI / z.ai): вопрос
допустимого провайдера оставался в БФТ открытым (3.1 №9), поэтому уже с MVP подключение
к ИИ сделано конфигурируемым, а на этапе 6 переехало в UI. Всё разворачивается в docker
и покрывается тестами.

### 1.1 Мини-глоссарий (термины документа)

- **Проверка по шаблону** — скриптовая, детерминированная проверка структуры документа
  (состав и порядок разделов) на соответствие эталону. Синонимы в истории коммитов:
  «шаблонная валидация», «template validation».
- **ИИ-проверка наполнения** — оценка содержимого документа моделью GLM (полнота,
  непротиворечивость, понятность). Синонимы: «оценка наполнения», «ai validation».
- **ИИ-критерий** — единица справочника «что именно проверяет ИИ»: название +
  промт (текст проверки). Активные критерии участвуют в сборке промта прогона;
  архивные — сохраняют смысл старых отчётов и оценок. Появился на этапе 8.
- **Оценка руководителя** — балл 1–5, выставляемый человеком по ИИ-критерию
  последнего прогона документа; «—» снимает оценку; новый прогон помечает
  прежние оценки устаревшими. Синоним: «человеческая оценка поверх ИИ».
- **Период дат** — окно «с … по …» включительно по дате создания документа
  в Confluence: date-only верхняя граница расширяется до конца суток
  («эффективная граница»), документы без даты создания в окно не попадают.
  На экране документов — с этапа 11; в статистике оценок период существовал
  с этапа 8 (по дате выставления оценки) и на этапе 11 переведён на дату
  создания документа.
- **Наблюдаемый прогон** — фоновая задача, чей старт страница видела живьём
  (событием SSE). Только финал наблюдаемого прогона вызывает реакцию UI — итог
  и перезагрузку; финал без наблюдаемого старта — это снимок состояния при
  (пере)подключении стрима, новостью он не является. Приём живёт с этапа 7,
  термин закреплён на этапе 10.
- **Руководитель группы аналитиков** — главный пользователь сервиса; в тексте также
  «руководитель». Рабочие псевдонимы той же роли в разных контекстах: «ревьюер»
  (когда речь о разборе документов) и «владелец процесса» (когда о настройке эталона).
- **Эталон (шаблон требований)** — модель ожидаемой структуры документа, по которой
  идёт проверка по шаблону. С этапа 9 шаблонов несколько: каждый — контейнер своей
  цепочки версий, у шаблона ровно одна активная версия; пометка «по умолчанию»
  задаёт предвыбор в диалоге запуска. Синонимы: «шаблон», «контейнер версий».
- **Роль** — именованный набор прав из фиксированного каталога; назначается
  пользователю при одобрении заявки и меняется позже. God — системная роль со
  всеми правами; остальные роли (включая стартовую Lead) редактируемы God-ом
  в таблице «право × роль». Появилась на этапе 15.
- **Общий реестр** — сквозной список всех шаблонов и ИИ-критериев всех
  пользователей: чужое в работе не видно, но можно найти и добавить себе копию
  (копия полностью независима). Появился на этапе 15.
- **Лид аналитика** — пользователь-куратор конкретного аналитика; очередь
  внимания и «Моя активность» лида строятся по его подопечным. Появился на
  этапе 15.
- **Фича-серия** — ветка в git + один или несколько тематических коммитов +
  слияние в main; единица истории продукта (см. раздел 18).
- **Кластер** — верхний уровень организационной структуры: объединяет команды;
  по смыслу синоним «департамента». Название уникально, цвет кодирует кластер
  в дереве и на картах. Появился на этапе 13.
- **Команда** — подразделение внутри кластера, объединяющее аналитиков;
  название уникально внутри своего кластера. Аналитик состоит ровно в одной
  команде (или «без команды»). Появилась на этапе 13.
- **Домен (аналитика)** — бизнес-функционал, за который отвечает аналитик,
  в виде свободного тега (список редактируется в профиле); домены команды на
  экране — объединение доменов её участников. Появился на этапе 13.

## 3. Этап 1 — MVP: сквозная проверка (21.08)

**Проблема.** Ценность сервиса доказуема только целиком: реестр аналитиков без
синхронизации бесполезен, синхронизация без проверки — вырождена, проверка без
отчёта и обратной связи — не завершена. Значит, первый этап обязан дать сквозной
процесс, а не отдельные кирпичи.

**Что построили** (за один день: 13 слитых фич-серий плюс 4 стартовых коммита
каркаса напрямую в main):

| Слой | Возможность | Бизнес-значение |
| ------ | ------------- | ----------------- |
| Данные | Каркас сервиса, модель данных, реестр аналитиков (CRUD) | От кого ждём документы — заведено в системе |
| Интеграция | REST-клиент Confluence Data Center; синхронизация страниц по расписанию и по кнопке | Документы появляются в сервисе сами, без ручного переноса |
| Список документов | Сортировка, пагинация, поиск | Руководитель находит нужный документ за секунды |
| Проверка по шаблону | Валидация структуры и заголовков по эталону (ФТ-CR-10) | Дешёвая, мгновенная, детерминированная проверка формы |
| ИИ-проверка наполнения | Оценка содержимого через GLM (ФТ-CR-11) | То, что раньше мог оценить только человек-эксперт |
| Оркестрация | Статусная модель, идемпотентность — не перепроверять неизменённое (ФТ-CR-14), автозапуск проверки после синхронизации (тогдашний ФТ-CR-12; отменён заказчиком на этапе 2) | Предсказуемые статусы; экономия на повторных прогонах |
| Обратная связь | Отправка итогов проверки комментарием на исходную страницу (механика ФТ-CR-17) | Замечание видит автор документа там, где он работает |
| Память | Заметки руководителя по документу, markdown (ФТ-CR-18) | Приватный контекст решений не теряется |
| Доступ | HTTP Basic поверх сервиса (НФТ-CR-7) | Сервис можно выносить в корпоративную сеть |
| UI | React SPA: аналитики → документы → отчёт с замечаниями | Пользователь работает глазами, а не curl'ом |
| Эксплуатация | Docker compose (backend + frontend + БД); README | Разворачивается одной командой; продукт можно показать |

Эталон шаблона на этом этапе был восстановлен «как есть» из реального шаблона
Confluence и положен в базу данных — как константа, не как управляемый артефакт
(эта несвобода станет проблемой этапа 3).

**Эффект этапа.** End-to-end ценность за один день работы: можно завести реального
аналитика, дождаться синхронизации, запустить проверку, увидеть отчёт и отправить
комментарий в Confluence. Продукт существует.

*Вывод этапа: сначала сквозная ценность, потом качество частей. Полный, но
неполированный продукт убеждает заказчика быстрее, чем идеальный каркас.*

## 4. Этап 2 — Стабилизация и первый разворот (22.08)

**Проблема.** MVP живёт в идеальном мире. Реальность: корпоративный SSL до
внутреннего Confluence, вход в UI, и главное — заказчик увидел продукт и
переосмыслил одно из базовых правил.

**Разворот: проверки запускаются только вручную.** В MVP проверка стартовала
автоматически после синхронизации. Заказчик сознательно отказался от этого:
неподконтрольные автоматические прогоны означают непредсказуемые счета за ИИ
и «замусоренный» свежими отчётами интерфейс. Проверка стала осознанным действием
человека: запустить — значит принять решение потратить ресурсы. Разворот был
компенсирован новыми возможностями запуска (та же фича-серия):

- **массовая проверка** всех документов аналитика одной кнопкой — фон, прогресс
  «K из N», актуальные документы пропускаются, ошибка одного не останавливает прогон;
- **кнопки «Проверить»/«Актуализировать» в каждой строке списка** документов;
- **изменившаяся в Confluence страница сбрасывает статус проверки** в «не проверено» —
  свежие правки не маскируются старым отчётом.

Идемпотентность (ФТ-CR-14) при этом сохранилась и теперь работает на экономию внутри
ручных прогонов. Требование об автозапуске (бывший ФТ-CR-12) из БФТ убрано.

*Книжный вывод: автоматизация — не всегда ценность; контроль момента расхода
дорогого ресурса бывает важнее.*

**Доработки этапа:**

| Фича | Проблема пользователя | Решение |
| ------ | ---------------------- | --------- |
| Форма добавления аналитика (ФТ-CR-1 в UI) | Завести аналитика мог только разработчик через API | Self-service руководителя |
| Бесконечная прокрутка вместо пагинации | Сотни документов — пагинация рвёт поток просмотра | Лента как в привычных инструментах |
| Отчёты рендерятся как markdown | ИИ-выводы с разметкой читались как сырой текст | Читаемые структурированные замечания |
| Заметки: видимость в списке, предпросмотр, удаление | Заметка была «чёрным ящиком» после сохранения | Полный жизненный цикл заметки |
| «Назад» возвращает прежнее состояние списка | Возврат из отчёта сбрасывал прокрутку и фильтры | Контекст работы не теряется |
| Семантический поиск через GLM | Подстрочный поиск не находит «документы про СМЭВ» словами «интеграция с гос. сервисами» | Вторая точка ценности ИИ: поиск по смыслу |
| Правка и удаление карточек аналитиков | Ошибка в ФИО/email требовала лазить в БД | Полный жизненный цикл реестра |

**Эксплуатационные фиксы этапа:** починен вход в UI; docker-контейнер научился ходить
во внутренний Confluence через корпоративную SSL-специфику — сервис реально встал
в окружение заказчика.

**Эффект этапа.** Сервисом можно пользоваться без разработчика рядом; стоимость
ИИ-проверок подконтрольна; интерфейс перестал сопротивляться объёмам.

## 5. Этап 3 — Настройка под реальный процесс (23.08)

**Проблема.** Эталонный шаблон, восстановленный из Confluence «как есть» (этап 1),
лежал в базе данных мёртвым грузом: изменить состав разделов мог только разработчик.
Но шаблон требований — живой артефакт процесса: команда меняет структуру документов,
и сервис обязан следовать за ней, а не наоборот.

**Что построили:**

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Редактор шаблона в UI | Маркер названия документа (шаблон-строка, по которой опознаётся заголовок) + структура разделов с drag & drop; каждое сохранение создаёт новую версию эталона — активна ровно одна, история версий видна в UI, отчёты проверки привязаны к конкретной версии | Владелец процесса сам меняет эталон; цикл «процесс изменился → сервис настроен» сжался с дней до минут; проверка воспроизводима — всегда известно, по какой версии эталона вердикт |
| Мягкие правила проверки | Неточные имена разделов, свободный порядок, уровни вложенности | Жёсткое «символ в символ» сравнение плодило ложные срабатывания и подрывало доверие к инструменту |

Ограничение этапа: повторяемые блоки доработок и служебные поля (name/description)
редактируются только в файле на сервере и переносятся из версии в версию без
изменений — эта часть эталона всё ещё требует разработчика.

**Эффект этапа.** Настройка сервиса перестала быть IT-задачей; шум ложных замечаний
снижен — руководителю не нужно перепроверять автомат «на честность».

*Вывод этапа: доверие к автоматической проверке зарабатывается не только точностью,
но и управляемостью эталона.*

## 6. Этап 4 — Редизайн в стиле Confluence (23.08)

**Проблема.** Функционально полный интерфейс на «своём» визуальном языке требовал
от руководителя учить новый язык. Пользователи сервиса живут в Confluence по
несколько часов в день — любой другой визуальный диалект — трение.

**Что построили:**

| Изменение | Содержание |
| ------ | ----------- |
| Редизайн по Atlassian Design System | Типографика, цвета, отступы и компоненты приведены к визуальному языку Confluence: кнопки, карточки, таблицы, поля ввода выглядят «как там» |
| Глобальный поиск по сервису | Одна точка входа для навигации: ищет объекты сервиса (аналитиков, документы, страницы настроек) по названию. Не путать с семантическим поиском этапа 2 — тот ищет по содержимому документов и работает через ИИ |
| Фикс вёрстки и адаптивности | Доводка редизайна: перестройки экранов на узких окнах, мобильная адаптация базовых экранов |

**Эффект этапа.** Порог принятия упал: сервис «выглядит как то, куда я и так хожу».
Глобальный поиск собрал разросшийся функционал в одну точку входа.

*Книжный вывод: редизайн — это не косметика, а снижение стоимости освоения:
знакомый интерфейс не нужно изучать.*

## 7. Этап 5 — Рабочее место ревьюера (24.08)

**Проблема.** Основной сценарий — «смотрю список, открываю документ, разбираю
замечания, возвращаюсь». Полноэкранная страница отчёта рвала этот цикл: между
списком и документом приходилось ходить туда-сюда. Навигация «вглубь» требовала
проходить через списки, хотя ментальная модель пользователя — «человек → его
документы».

**Что построили:**

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Два режима просмотра | Панель документа справа от списка + полноэкранная страница; хлебные крошки «Аналитики / автор / документ» и блок автора с именем и email | Быстрый взгляд не теряет контекст списка; глубокая работа — на полном экране; ориентация в чужом документе |
| Ресайз панели просмотра | Ширина регулируется (мышь и клавиатура, запоминается); переход на полную страницу — кликом по названию документа в хлебных крошках, отдельная кнопка убрана как неинтуитивная | Широкие таблицы требований не ломают верстку; путь к полному экрану — там, куда и так смотрит глаз |
| Редизайн панели | Зоны, «воздух», липкая шапка | Часовая работа с документом без утомления и потери ориентации |
| Дерево «Аналитики → документы» | Навигация в сайдбаре (ленивая, с кэшем) + ресайз ширины сайдбара | Ментальная модель «файловый менеджер»: от человека к его документам за один клик |

**Эффект этапа.** Сервис из «каталога отчётов» превратился в рабочее место, где
проводят день.

*Вывод этапа: производительность ревьюера определяется не количеством функций,
а стоимостью переключения между ними.*

## 8. Этап 6 — Конфигурируемость проверок и ИИ (24.08)

**Проблема.** Три настройки, влияющие на стоимость и качество прогона, были
недоступны из UI: состав документов на проверку, параметры проверки (шаблон, промт
ИИ) и подключение к ИИ-провайдеру (протокол, URL, токен, модель жили в `.env`

| Выборочная проверка | Чекбоксы документов; выбор шаблона и промта ИИ перед запуском | Прогон = осознанный набор документов и настроек; стоимость управляется |

категория тикетов в поддержке.*

## 9. Этап 7 — Точность и живость (25–26.08)

**Проблема.** Две оставшиеся шероховатости: (а) проверка всегда гоняла оба фактора —
быструю проверку по шаблону и дорогую ИИ-оценку — хотя иногда нужен только один;
(б) итог фонового прогона пользователь узнавал, вручную перезагрузив страницу
(F5 как «кнопка обновить данные»).

**Что построили:**

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Выбор критериев проверки | Проверка по шаблону и/или ИИ-проверка наполнения; минимум один обязателен | Быстрая скриптовая проверка — отдельно от дорогой ИИ-оценки; семантика «не запускалась» отличима от «не пройдено» |
| Живые события (SSE) | Стрим `/api/events`; итоги проверок и синхронизаций приходят на открытую страницу сами | Убрана последняя ручная операция наблюдения; интерфейс «живой»: запустил — и увидел, когда готово |

**Технологический выбор, о котором стоит упомянуть в книге:** серверные события (SSE)
через fetch-стрим вместо WebSocket и поллинга — однонаправленный поток событий от
сервера не требует двустороннего протокола и пробрасывает авторизацию так же, как
обычный REST-запрос.

**Эффект этапа.** Проверка «только шаблон» по 50 документам стоит копейки и минуты;
результат любого фонового прогона появляется сам. Сервис дошёл до состояния
«реагирует», а не «ждёт, пока догадаются обновить».

*Вывод этапа: последние проценты полировки — точность критериев и мгновенность
отклика — ощущаются пользователем сильнее, чем десяток новых функций.*

## 10. Этап 8 — Контур управления качеством (28.08)

**Проблема.** Сервис к этому моменту хорошо отвечал на вопрос «соответствует ли
документ требованиям» — но сам процесс оценки качества оставался непрозрачным
и односторонним. Три разрыва:

1. **Что проверяет ИИ — зашито в промт.** Список аспектов проверки (полнота,
   непротиворечивость, однозначность) был константой кода: добавить критерий
   «проверяемость требования» или временно исключить один — задача разработчика
   с деплоем. Эталон шаблона к этому моменту уже был управляемым артефактом
   (этап 3), а «эталон наполнения» — нет: асимметрия.
2. **Мнение машины — без следа человека.** Руководитель читал ИИ-отчёт,
   соглашался или спорил с ним — молча. Его экспертная оценка не фиксировалась
   нигде: ни по документу, ни тем более в агрегированном виде по аналитику.
3. **Нет оценок — нет накопления.** У кого из аналитиков стабильно проседает
   полнота, а у кого однозначность формулировок — держалось в памяти
   руководителя. Кадровый разговор «вот твои слабые места по оценкам за
   квартал» нечем было подкрепить.

**Что построили** (одна серия `feat/ai-criteria`, вошла четырьмя коммитами —
по фазе):

| Фаза | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Справочник ИИ-критериев | Глобальный список «название + текст проверки (промт)»: создание, правка, архивация; удаление заменено архивом — история старых отчётов не теряет смысла; сидирован тремя стартовыми критериями (полнота описания, непротиворечивость требований, однозначность формулировок); страница «Критерии ИИ-проверок» в разделе настройки | «Эталон наполнения» стал управляемым артефактом наравне с эталоном шаблона; цикл «процесс изменился → проверка настроена» — без разработчика |
| Выбор критериев и живой промт | В диалоге запуска — чекбоксы критериев; итоговый промт показан целиком и пересобирается на лету при включении/отключении; отжатый критерий исключается и из прогона, и из блока оценки в отчёте; правка собранного промта — «под замком»: сначала явная разблокировка | Прогон проверяет ровно то, что выбрано, и руководитель видит, за что платит; случайная правка пересобранного промта исключена |
| Оценки руководителя | Блок «Оценка руководителя» в отчёте: по каждому критерию последнего прогона — балл 1–5 или «—» (снять); повторный прогон документа помечает прежние оценки устаревшими, а не сбрасывает | Мнение человека фиксируется рядом с мнением ИИ и всегда соотнесено с конкретным прогоном |
| Профиль и статистика аналитика | Профиль: карточка (email, Confluence, число документов, синхронизация) + заметки руководителя об аналитике (markdown, приватные — по образцу заметок по документу, ФТ-CR-18). Статистика: общий средний балл и средние по критериям за произвольный период, сортировка от сильных к слабым, архивные критерии помечены | Приватная память о людях; накопленные оценки превращаются в аргументированные цифры для разговора о развитии; фильтр по периоду даёт «за квартал» без доработок |

**Решения, о которых стоит упомянуть в книге:**

- **Архив вместо удаления** — тот же приём, что и в версиях эталона: сущность,
  на которую ссылаются исторические отчёты и оценки, не уничтожается, а
  переводится в пассивное состояние.
- **«Устаревание» вместо сброса.** Новый прогон мог бы молча обнулить оценки —
  вместо этого они остаются видимыми с пометкой: история наблюдений ценнее
  формальной чистоты данных.
- **Оценка привязана к критерию и прогону, статистика — к дате выставления.**
  Фильтр периода в статистике отсчитывается по дате оценки: руководитель мог
  оценить документ недельной давности сегодня — в статистику попадёт «сегодня».
  Снятые «—» записями не являются и в средние не попадают.

**Эффект этапа.** Замкнулся контур управления качеством: автоматическая оценка
документов (этапы 1–7) → человеческая оценка поверх автоматической →
агрегированная статистика по аналитикам. Сервис перерос «инструмент проверки»
и стал системой управления качеством требований.

*Вывод этапа: автоматизация оценки — только половина контура; полную ценность
ей придаёт зафиксированное человеческое суждение, накапливающееся в статистику.*

## 11. Этап 9 — Мультишаблоны требований (31.08)

**Проблема.** Эталон стал управляемым артефактом ещё на этапе 3 — но остался
единственным. Группа же ведёт не один тип документов: системные требования,
доработки интеграций, описания сервисов — у каждого типа своя структура разделов.
Проверка «всех по одному эталону» означала ложные замечания в корректных документах
другого типа — ровно тот шум, от которого избавились мягкими правилами этапа 3, —
либо перенастройку эталона перед каждым прогоном «не того» типа. Выбор шаблона
в диалоге запуска (этап 6) при единственном существующем шаблоне оставался
формальностью.

**Что построили** (одна серия `feat/multi-templates`):

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Контейнер шаблонов | Сущность «шаблон» объединяет цепочку версий эталона; шаблонов несколько, у каждого ровно одна активная версия — внутри своего шаблона; название и описание редактируются версиями, история помнит имя на момент проверки; живая база мигрировала при старте контейнера — существующая цепочка версий завернулась в шаблон №1 без потерь | Несколько типов документов — несколько эталонов одновременно; воспроизводимость проверок и история правок сохранены |
| Управление набором | Раздел «Шаблоны требований»: лента карточек с горизонтальным скроллом, создание с нуля, архивация вместо удаления и восстановление из архива; пометка «по умолчанию» — предвыбор в диалоге запуска; при архивации дефолта пометка переходит на самый свежий оставшийся шаблон | Владелец процесса ведёт справочник эталонов сам; исторические отчёты не теряют смысла после любых перестроений набора |
| Выбор при проверке | В диалоге запуска — карточки-радио: шаблон выбирается до прогона, архивные в выборе не участвуют; дубль названия (без учёта регистра) и дубль разделов отклоняются с понятной ошибкой | Прогон проверяет документ по нужному эталону; случайная порча справочника исключена |

**Решения, о которых стоит упомянуть в книге:**

- **Архив вместо удаления — третий виток приёма** (версии эталона — этап 3,
  ИИ-критерии — этап 8, шаблоны — этап 9): сущность, на которую ссылаются
  исторические отчёты, не уничтожается, а переводится в пассивное состояние.
- **Миграция данных «на лету»:** живая postgres-база обновилась при старте
  контейнера — идемпотентные миграции (новая колонка, завёртывание версий
  в контейнер) выполняются при инициализации и безопасно пропускаются при
  повторном старте.
- **Обратная совместимость контракта:** legacy `/api/template` продолжает
  отвечать за шаблон по умолчанию — внешние потребители не заметили смены
  модели данных.

**Эффект этапа.** Проверка по шаблону перестала быть «один размер для всех»:
под каждый тип документа — свой эталон, выбираемый в момент запуска. Справочник
эталонов стал таким же управляемым активом, как реестр аналитиков и справочник
ИИ-критериев.

*Вывод этапа: эталон — не константа процесса, а растущий справочник; сервис
следует за разнообразием документов, а не наоборот.*

## 12. Этап 10 — Синхронизация на рабочем экране (31.08)

**Проблема.** К этому моменту почти весь рабочий цикл ревьюера собрался на одном
экране: документы аналитика, панель просмотра, запуск проверки из строки и из
диалога, живые итоги прогонов. Но синхронизация осталась привязана к списку
аналитиков: заметив на экране документов устаревший набор, руководитель должен
был уйти на другой экран, найти там нужную строку, нажать кнопку и вернуться.
Цикл «вижу устаревшее → подтягиваю свежее → проверяю» рвался навигацией ещё
в одном месте.

**Что построили** (одна серия `feat/documents-sync-button`):

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Кнопка в шапке экрана документов | «⟳ Синхронизировать» рядом с «Проверить выбранные» — зеркало кнопки со списка аналитиков; на время прогона заняты обе кнопки шапки | Синхронизация происходит там, где идёт работа; уход со экрана ради служебной кнопки исчез |
| Итог прогона на месте | Зелёная строка «Синхронизация завершена: новых N, обновлено M» либо красная с ошибкой; подзаголовок «Всего документов: N · Синхронизировано: дата» | Результат виден без переходов; свежесть данных — в одном взгляде с объёмом |
| Живое состояние по SSE | Занятость и финал приходят событиями: синхронизация, запущенная из другой вкладки или расписанием, тоже отражается; по финалу наблюдаемого прогона список и данные аналитика в шапке (дата последней синхронизации) перечитываются | Модель «живого» UI (этап 7) распространилась на новый элемент без нового механизма |

**Решения, о которых стоит упомянуть в книге:**

- **Итог — в собственном состоянии, а не в общем `error`.** Обработчик финала
  одновременно перечитывает список, а успешная перезагрузка чистит общий error —
  красное сообщение о сбое синхронизации жило бы ровно один HTTP-запрос.
  Зелёный итог в отдельном состоянии жил и раньше — асимметрия подсказала
  правильный контур состояния.
- **«Наблюдаемый прогон» и флаг в ref.** Подписка на SSE пересоздаётся на каждое
  нажатие клавиши в поиске (меняется идентичность колбэка загрузки) — флаг
  «видели старт», живший в замыкании эффекта, терялся при правке фильтров, и
  финал молча игнорировался: ни итога, ни перезагрузки. Ref переживает
  пересоздание подписки.
- **busy до запроса, а не после ответа.** Между кликом и ответом 202 кнопка
  оставалась активной: повторный клик порождал 409 «уже выполняется», а финал
  SSE, обработанный раньше ответа, «воскрешал» занятость навсегда — обе кнопки
  шапки оставались недоступны до перемонтирования.
- **Наивный UTC читается как UTC.** Бэкенд хранит время без зоны; новый
  подзаголовок дописывает суффикс Z перед парсингом — время совпадает со
  стенными часами пользователя, а не сдвигается на его часовой пояс.
- **Состязательное ревью мелкой фичи.** Дифф примерно в 300 строк ушёл в
  ревью-воркфлоу (несколько независимых линз + скептическая верификация каждой
  находки кодом и мутационными тестами): 12 подтверждённых находок, из них
  четыре — про состояние и гонки, которые существовавшие юнит-тесты «зеленили»
  по транзиентному рендеру. Тесты усилены так, что каждая из найденных
  мутаций-регрессий роняет suite.

**Эффект этапа.** Последний служебный переход в цикле ревьюера убран: экран
документов аналитика стал самодостаточным — от свежести данных до запуска
проверки и её итога.

*Вывод этапа: зрелость проявляется не только в новых сущностях, но и в стирании
последних трений; настоящая цена мелкой фичи видна только на граничных кейсах —
гонках, чужих событиях и сбоях.*

## 13. Этап 11 — Период дат: работа без ретроспективы (31.08)

**Проблема.** Руководитель проверяет работу аналитиков за окно — неделю, месяц,
квартал, — а не за всю историю. К этому моменту оба места, где ретроспектива
мешала, не умели отвечать на вопрос «за период»:

1. **Список документов не фильтровался по датам.** Чтобы разобрать только
   документы последних недель, руководитель визуально сканировал реестр:
   сортировка по дате создания помогала, но окно приходилось держать в голове.
2. **Статистика фильтровалась не по тому событию.** Период в «Статистике
   оценок» (этап 8) отсчитывался по дате выставления оценки: документ,
   созданный в мае и оценённый в августе, попадал в августовскую статистику.
   Для вопроса «как аналитик работал в августе» это неверный набор данных:
   ретроспективные документы притягивались к дате разбора, а свежие, ещё
   не разобранные, из статистики выпадали.

Заказчик сформулировал цель прямо: «проверять, что и как сделали аналитики,
указывая период дат, чтобы не учитывать всю ретроспективную работу» — и
подтвердил замену семантики статистики на дату создания документа, без
переключателя режимов.

**Что построили** (одна серия `feat/period-filter`):

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Период на экране документов | Поля «Создан с»/«по» рядом с «Название»/«Ссылка»: фильтр по дате создания в Confluence, границы включительны; период живёт в адресе страницы — переживает «Назад» и закладки; в режиме семантического поиска поля недоступны (период в нём не участвует); пустая выборка — «За выбранный период документов нет» | Разбор только свежих документов без сканирования реестра; ссылкой на отфильтрованный срез можно поделиться |
| Смена семантики статистики | Период «Статистики оценок» переведён с даты выставления оценки на дату создания документа; подпись страницы проговаривает это явно — «документы созданы: … — …»; пустая выборка — «За выбранный период оценок нет», сброс — «За всё время» | «Как работал аналитик в августе» = документы, созданные в августе, независимо от того, когда их разобрали; кадровые цифры не зависят от даты разбора |
| Применённый период ≠ черновик | Подпись, пустое состояние и кнопка «За всё время» описывают загруженные данные; очистка полей без «Применить» тексты не меняет | Интерфейс не утверждает о данных того, чего в них нет |
| Контракт периода на сервере | Верхняя date-only граница расширяется до конца суток — «по 31.08» включает 31-е целиком; границы принимаются и наивными, и со смещением зоны («Z», «+03:00») — приводятся к UTC; перевёрнутый период отклоняется 422 с понятным текстом; в статистике оценок ответ эхом возвращает эффективную границу (список документов границу не возвращает — период там живёт в URL страницы) | Включительность «по дате» — одно правило в одном месте (сервер), а не в каждом клиенте; закладки и внешние клиенты минуют UI-валидацию, поэтому guard не переезжает в браузер |

**Решения, о которых стоит упомянуть в книге:**

- **Наивные и осведомлённые datetime — мина под любым период-фильтром.**
  pydantic парсит «2026-08-31» и «2026-08-31T00:00:00Z» в разные типы
  (naive и aware); их смешение роняет сравнение в Python (TypeError →
  HTTP 500), а aware-граница в SQL-сравнении с наивной колонкой молча
  теряет смещение — окно съезжает. Решение: приведение к наивному UTC
  до первого использования — и до guard, и до SQL. Найдено состязательным
  ревью; «зелёные» на тот момент тесты смешение не покрывали.
- **NULL-даты выпадают из окна — осознанно.** Документ без даты создания
  не попадает ни в какой период (SQL-семантика NULL), но виден без
  фильтра. Решение принято явно и зафиксировано докстрингами и тестами,
  а не замолчано.
- **Смена семантики без смены контракта.** Параметры `date_from`/`date_to`
  статистики не переименовывались: внешние клиенты не заметили перемен;
  новый смысл проговорён в докстрингах, а эхо периода возвращает
  эффективную границу — ответ честно описывает применённый фильтр.
- **Вина пустого результата.** «За выбранный период документов нет»
  появляется только когда других фильтров нет: пустота из-за опечатки
  в «Названии» не должна обвинять период.
- **Состязательное ревью мелкой фичи — снова 12 подтверждённых находок**
  (плюс две отвергнутых верификаторами): от 500 на смешении naive/aware
  до «[object Object]» вместо текста ошибки в UI. Как и на этапе 10,
  находки концентрировались не в счастливом пути, а на границах: чужие
  форматы дат, черновик против применённого фильтра, ложная вина пустого
  результата.

**Эффект этапа.** Руководитель задаёт окно дат и получает в нём оба ответа:
что аналитик сделал (список созданных документов) и как сделал (статистика
оценок по этим документам). Формулировка «проверить работу за квартал»
перестала требовать вычитания ретроспективы из полной картины.

*Вывод этапа: периодизация — не фильтр среди фильтров, а смена вопроса:
от «всё, что есть» к «что произошло в окне». Семантика окна — по какому
событию оно отсчитывается — важнее его механики; ошибка в семантике не
ломает ни один тест и потому особенно коварна.*

## 14. Этап 12 — Архитектура по слоям (03.09)

**Проблема.** К одиннадцатому этапу функционал сервиса вырос, а организация кода —
нет: SQL-запросы жили прямо в роутерах, «сервисы» смешивали бизнес-логику с
обращением к базе, модели и API-схемы были монолитными файлами, авторизация —
middleware поверх фреймворка. Пока команда была «один разработчик + ИИ», это
терпимо; но каждая новая фича начиналась с вопроса «где это вообще лежит», а цена
ошибки росла с каждым слоем, положенным не на место. Заказчик сформулировал
требование жёстко: «проект разбит по слоям: api, dependencies, usecase, repository,
models, schemas» — и зафиксировал процесс: рефакторинг в отдельной ветке, тесты
зелёные после каждого шага.

**Что построили** (одна серия `refactor/backend-clean-architecture`, вошла
восемью коммитами — по слою):

| Коммит | Содержание | Правило слоя |
| ------ | ----------- | -------------- |
| models/, schemas/ | Монолиты разрезаны на пакеты по доменам (analysts, documents, validation, templates, ai) с фасадами `__init__` — импорты потребителей не изменились | Данные и контракты API — отдельно от логики |
| clients/ | Confluence, GLM-валидатор и семантический поиск вынесены из «сервисов»; клиенты знают только конфиг | Внешние системы — за одним барьером, с транспортными исключениями |
| dependencies/ + auth | HTTP Basic переписан с middleware на FastAPI-зависимости; get_db — зависимость; паритет ответов 401/404 сохранён один в один (включая /docs и неизвестные пути) | Авторизация — явная зависимость, а не невидимая обёртка |
| usecase + repository | Бизнес-логика и сценарии — в usecase; SQL — только чтение в repository; запись (add/commit) осталась в usecase; доменные исключения — в одном месте, api переводит их в HTTP | Логика тестируется без HTTP; SQL не размазан по роутерам |
| api/ | Роутеры стали тонкими обёртками: парсинг входа и маппинг исключений; фоновой оркестратор (tasks/sync) — единственное зафиксированное исключение, открывающее свою сессию | HTTP-слой не принимает решений |

Миграция шла серией маленьких шагов: каждый коммит — законченный слой, после
каждого 281 тест зелёный, в конце — docker-пересборка и живой смоук (401-паритет,
SSE, прогон проверки). Контракты API и тексты ошибок не изменились ни разу —
внешний потребитель не заметил перестройки.

**Решения, о которых стоит упомянуть в книге:**

- **Тесты как гарант, а не смелость.** Перестройка вслепую невозможна; каждый
  шаг опирался на зелёный suite, а правки тестов допускались только для путей
  импортов и сигнатур подмен — ассертации не смягчались ни разу.
- **Фасады вместо массовой правки импортов.** Пакетные `__init__` сохраняют
  старые точки входа (`from app.models import Analyst`) — потребители переехали
  без единой правки.
- **Паритет 401/404 как требование.** Переход с middleware на dependencies
  ломал три неочевидных случая (стрим SSE, /docs, неизвестные пути) — каждый
  закрыт явно и покрыт тестами.

**Эффект этапа.** Новые фичи (следующий этап — сразу проверка) легли по слоям
без «а куда это положить»: модель → repository/usecase → api → UI. Цена навигации
по коду и онбординга упала; правила слоёв зафиксированы скиллом с grep-чеклистом.

*Вывод этапа: рефакторинг — не генеральная перестройка, а серия маленьких зелёных
шагов; архитектура держится не дисциплиной памяти, а правилами, записанными
снаружи головы.*

## 15. Этап 13 — Кластеры и команды (03–04.09)

**Проблема.** Руководитель видел аналитиков плоским списком — хотя реальная
организация трёхуровневая: департаменты (в сервисе — «кластеры»), внутри них
команды, внутри команд аналитики со своими доменами (бизнес-функционалом).
Плоский список не отвечал ни на вопрос «кто чем занимается», ни «куда посадить
нового аналитика», ни «чьи документы я сейчас смотрю». Кроме навигации, страдала
и семантика: принадлежность к команде — часть данных, а не украшение интерфейса.

Решения заказчика до разработки: домены — у каждого аналитика (свободные теги,
не справочник); аналитик состоит ровно в одной команде; верхний уровень зовётся
«кластер». UI согласован HTML-макетом до кода — все четыре экрана и попапы.

**Что построили** (две серии: `feature/teams-hierarchy` — пять коммитов:
backend, два frontend-коммита, профиль, фикс-ревью; `feature/teams-ux-feedback` —
два коммита: backend-пачки, frontend UX):

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Модель структуры | Таблицы «кластер» (название уникально без регистра, цвет из палитры UI) и «команда» (уникальна в кластере); у аналитика — ссылка на команду (NULL — «без команды») и список доменов-тегов; миграция живой базы — идемпотентными ALTER при старте | Структура — данные, а не подписи в интерфейсе; существующие аналитики не теряются (попадают в «Без команды») |
| Карта кластеров (главная) | Вместо списка аналитиков — цветные плитки кластеров со счётчиками (команды/аналитики/документы) и мини-схемой команд; кликабельна целиком; секция «Без команды»; нечёткий поиск по кластерам, описаниям и командам | Первый экран отвечает «кто есть в организации» одним взглядом; опечатки в поиске не мешают |
| Дерево в сайдбаре | «Кластер → команда → аналитик → последние документы»: прежние ленивые ветки документов вложены в уровни структуры; ветка «Без команды»; ссылка «Все аналитики» сохранена; дерево обновляется само после мутаций структуры (событие org-changed) | Навигация «файловым менеджером» (этап 5) продлена на структуру; ничего не потеряно от старого дерева |
| Экраны кластера и команды | Кластер: шапка со счётчиками, команды-«колонны» с составом; команда: aggregated домены участников, карточки аналитиков с тегами; всё управляемо — CRUD кластеров и команд, пополнение команды прямо из карточки кластера | Управление структурой — там же, где её просмотр; второй способ наполнить команду без перехода |
| Профиль аналитика | Хлебные крошки «Кластеры / кластер / команда / ФИО» с переходами; домены — чипы с автосохранением (добавление по Enter, без кнопки «сохранить») | Причастность видна и кликабельна из любого места; правка доменов — в моменте |
| Массовое добавление | Модалка добавления — с чекбоксами: несколько аналитиков одной отправкой (backend принимает пачку до 50, атомарно); уже состоящие в команде заблокированы; пустой список доменов = «не трогать» существующие теги | Наполнение команды из десятка людей — одно действие, а не десять |
| Guard'ы данных | Кластер удаляется только пустым (409 с подсказкой); удаление команды отвязывает участников, сохраняя их домены, документы и оценки; перевод аналитика между командами не трогает его историю | Структуру можно перестраивать без страха за данные людей |

**Решения, о которых стоит упомянуть в книге:**

- **Домены команды — производное, а не ещё одно поле.** Список доменов команды
  не хранится: он собирается из доменов участников. Одна истина — у аналитика;
  расхождение чипов на разных экранах невозможно по построению.
- **NULL как состояние «без команды».** Вместо фиктивной «команды по умолчанию» —
  честный NULL и отдельная ветка/секция: аналитик вне структуры остаётся видимым
  и доступным для перевода.
- **Удаление без каскада по людям.** FK без ON DELETE: usecase явно отвязывает
  участников перед удалением команды — поведение видно в коде и в тестах, а не
  спрятано в каскаде СУБД.
- **Событие вместо прокидывания колбэков.** Сайдбар живёт вне роутов и не
  перемонтируется; мутации структуры диспатчат `org-changed` — дерево перечитывает
  себя сам, без гонок и ручных обновлений.
- **Согласование макета до кода.** Четыре экрана в одном HTML-файле с данными
  из реального примера — заказчик утвердил форму до реализации; правки после
  («верните документы в дерево и профиль») обошлись точечно.
- **Состязательное ревью большой фичи:** 37 кандидатов от восьми линз, после
  верификации — 17 подтверждённых; исправлены стирание доменов при переводе,
  регистрозависимая уникальность кластеров, N+1-запросы на списках, устаревшие
  хлебные крошки на нетронутых фичей экранах.

**Эффект этапа.** Сервис стал отражать организацию: руководитель управляет
структурой (создал кластер — завёл команды — раздал аналитиков), ходит по ней
из любого экрана и ищет по ней нечётко. Плоский список остался как реестр —
«Все аналитики» — но навигация и семантика переехали на структуру.

*Вывод этапа: иерархия — это не поле в карточке, а способ передвижения по
системе; когда структура становится данными, она автоматически становится
и навигацией, и поиском, и отчётностью.*

## 16. Этап 14 — Пульт руководителя (09.09)

**Проблема.** Сервис вырос до тринадцати экранов, но «дома» не имел: главная
страница была просто ещё одним разделом (карта кластеров), а хлебные крошки
начинались то с «Кластеров», то с «Аналитиков», то с имени пространства —
вернуться «в начало» и понять, где находишься, было невозможно. Итоги фоновых
прогонов жили только в момент события: пришёл позже — узнаешь, только открыв
документ.

**Целевой вид** согласовали HTML-макетом: главная — пульт, отвечающий на три
вопроса — *что требует внимания / что происходит сейчас / где что лежит*.

**Что построили** (одна серия `feature/home-dashboard`, вошла пятью коммитами —
backend, frontend, крошки, ревью-фиксы):

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Очередь внимания | Агрегат `/api/dashboard`: пять секций — проваленные проверки (с причиной), устаревшие после правок в Confluence, ждут оценки руководителя, аналитики без команды, проблемы справочников | Открыл сервис — видишь, за что браться; работа с исключениями вместо сканирования реестра |
| Живая лента | Журнал последних событий фоновых задач (пишется всегда, даже без подписчиков) + SSE-дополнение на открытой странице | События получили адрес в интерфейсе: пришёл позже — видишь, что пропустил |
| «Сейчас происходит» | Статусы синхронизации и массовой проверки | Служебные состояния видны без переходов |
| Единые крошки | Корень «🏠 Главная» на всех экранах; крошка несёт тип объекта («Команда GDS», «Отчёт: …»); логотип ведёт на главную | Путаница «где я» исчезла; возврат в начало — один клик |
| Карта страницы | «Недавние» (localStorage), свёрнутая структура, сервисные карточки с живыми счётчиками | Быстрые входы туда, куда реально ходишь |

**Решения, о которых стоит упомянуть в книге:**

- **Агрегатный эндпоинт вместо десяти запросов**: очередь собирается одним
  `/api/dashboard` из пяти приоритетных выборок (провал → устарел → ждёт
  оценки; документ попадает только в первую подходящую секцию), лимит строк
  на секцию с честным полным счётчиком.
- **Журнал пишет всегда** — даже когда SSE-подписчиков нет; ранний выход
  «нет подписчиков — выйти» заменили записью в кольцевой журнал.
- **Состязательное ревью поймало 500** на пограничном состоянии (больше 8
  проблемных шаблонов валили весь дашборд схемой ответа) — закрыто
  регрессионным тестом; плюс фикс «шторма» перезагрузок при массовой
  проверке (дебаунс) и снимков SSE, рисовавших фальшивые события ленты.

**Эффект этапа.** Сервис обзавёлся точкой входа и точкой возврата: руководитель
начинает день с очереди внимания, а не с выбора раздела; любое событие фоновых
задач доживает до своего читателя.

*Вывод этапа: главная страница — не обложка, а рабочая очередь; навигация
здоровает, когда у неё один корень, а «сейчас» — это тоже данные.*

## 17. Этап 15 — Многопользовательскость и роли (10.09)

**Проблема.** Инструментом пользовался один человек: один логин/пароль в env,
один сервисный токен Confluence, один справочник шаблонов и ИИ-критериев,
одна настройка ИИ. Дать доступ лидам групп означало раздать собственный пароль
и лишить каждого своего эталона и своего ключа ИИ. Требовался переход к
целевому виду: **сервис для всех лидов**, где у каждого свой вход, свои
эталоны, свой ИИ — и общая структура с общей очередью.

Решения заказчика до разработки (макет, 11 экранов): God входит логином и
паролем — как раньше; лиды входят **персональным токеном Confluence**; первый
вход по токену создаёт **заявку на модерацию** (из токена Confluence
достаются ФИО, почта, логин); отклонённые могут подать повторно; шаблоны и
критерии — **персональные**, с **общим реестром** для копирования; **без
настроенного личного ИИ проверки не запускаются**; у аналитика — **лид**;
главная фильтруется по подопечным.

**Что построили** (одна серия `feature/auth-roles`, вошла одиннадцатью
коммитами: backend-каркас, владельцы и права, frontend auth, страницы, правки
по замечаниям и ревью):

| Фича | Содержание | Бизнес-значение |
| ------ | ----------- | ----------------- |
| Вход и сессии | God — логин+пароль из env; лиды — токен Confluence (проверка через `whoami`, хранится sha256-хэш); Bearer-сессии в БД вместо HTTP Basic | Понятный вход «своим» токеном; сессию можно отозвать |
| Заявки на модерацию | Незнакомый токен → заявка с данными из Confluence; God принимает (с выбором роли) или отклоняет; отклонённые подают повторно; на главной God — счётчик новых заявок | Доступ выдаётся осознанно, а не раздачей пароля |
| Динамические роли | Каталог прав; матрица «право × роль»: God системная (всё), остальные — редактируемые столбцы; роль нельзя удалить, пока она назначена | Права настраивает владелец сервиса, а не разработчик |
| Персональные шаблоны и критерии | Владелец у каждого; работа только со своими; **общий реестр** — все шаблоны/критерии всех с копированием себе; своё — архивируется | У каждого лида свои эталоны и критерии, не мешая другим; лучшие практики распространяются копированием |
| Персональный ИИ | Свой провайдер/модель/токен (шаги 01–03 прежнего дизайна); без настроенного доступа ИИ-проверка блокируется с понятной ошибкой; God правит «настройку по умолчанию» | Каждый лид платит со своего ключа и выбирает свою модель; чужие токены не расходуются |
| Лид аналитика | В профиле — куратор (назначение поиском среди пользователей); у лида на главной — «Мои аналитики» и «Моя активность» | Зона ответственности лида выражена данными, а не договорённостью |
| Персональная очередь | Документные секции очереди внимания лида — только по подопечным; God видит всё; «без команды» и справочники — общие | Лид видит своих, руководитель — всех |

**Решения, о которых стоит упомянуть в книге:**

- **Токен — это пароль лида.** В БД только sha256-хэш; вход повторным токеном
  сравнивает хэши. Личность подтверждает сам Confluence (`whoami` тем же
  токеном) — отдельный пароль вводить не нужно.
- **Роль = JSON-набор прав из каталога.** Вместо жёстких «god/lead» в коде —
  таблица «право × роль»: новый столбец = новая роль. Проверка права —
  зависимость над эндпоинтом (`require_permission`), при выключенной
  авторизации (тесты/локально) — пропуск.
- **Владелец как параметр выборок.** Персонализация не отдельная «модуль
  тенантов», а колонка `owner_user_id` и фильтр в repository; общий реестр —
  та же таблица без фильтра + копирование. Миграция: весь существующий
  контент достался God-пользователю.
- **Guard вместо молчаливой ошибки.** Без личного ИИ запуск ИИ-проверки
  возвращает 409 «настройте доступ» — вместо падения посреди прогона;
  сохранение личной строки наследует пустые поля из настройки по умолчанию,
  чтобы «визуально заполненная форма» не оставляла пользователя навсегда
  заблокированным.
- **Выключаемая авторизация.** `AUTH_ENABLED=false` (тесты, локальная
  разработка) превращает пользователя в системного God и пропускает проверку
  прав: весь накопленный тестовый парк жил дальше без единой правки.

**Эффект этапа.** Барьер «инструмент на одного» снят: лиды входят своими
токенами Confluence, работают со своими эталонами и своими ключами ИИ,
видят своих аналитиков — при общей структуре, общей очереди служебных
проблем и едином инструменте. Пароль сервиса больше никому не передаётся.

*Вывод этапа: многопользовательскость — это не логин-экран, а разделение
трёх сущностей: идентичность (вход), полномочия (роли) и владение (чей
шаблон, чей ключ ИИ, чей аналитик). Когда эти оси разделены, новые роли —
это столбец в таблице, а не релиз.*

## 19. Сквозные инженерные принципы (нить для книги)

Эти правила действовали всю историю проекта и объясняют его форму:

1. **Одна фича — одна ветка — один коммит**, слияние через `merge --no-ff`.
   Исключения известны и перечислены: 4 стартовых коммита каркаса, сервисные
   правки и серии с несколькими коммитами (`feat/confluence-sync` вошла
   feat- и fix-коммитами, `feat/ai-criteria` — четырьмя feat-коммитами по фазам,
   `refactor/backend-clean-architecture` — восемью по слоям,
   `feature/teams-hierarchy` — пятью: backend, три фронтенд-этапа, ревью-фиксы).
   Благодаря политике веток git-история читается как оглавление
   продукта — раздел 18 буквально собран из `git log`.
2. **Безопасность прежде всего:** секреты только в локальном `.env` (gitignored);
   закрытый репозиторий; учётки не попадают в логи и транскрипты.
3. **Всё в docker и с тестами:** каждый этап завершался прогоном автотестов
   backend и frontend плюс сквозной проверкой в реальном браузере против
   docker-стека.
4. **GLM — рабочий ИИ-провайдер** (вопрос провайдера в БФТ открыт, 3.1 №9),
   подключение конфигурируемо: протокол/URL/токен/модель через UI.
5. **Обратная совместимость контрактов:** новые поля опциональны, старые
   клиенты не ломаются при эволюции API.
6. **Фон вместо блокировки:** длинные операции (синхронизация, проверки) — фоновые
   задачи со статусами; UI никогда не ждёт ответа минутами.
7. **Архив вместо удаления:** сущность, на которую ссылаются исторические отчёты
   и оценки, не уничтожается, а переводится в пассивное состояние. Три витка
   приёма: версии эталона (этап 3), ИИ-критерии (этап 8), шаблоны (этап 9).
8. **Чистая архитектура как закон, а не пожелание** (с этапа 12): слои
   api → usecase → repository → models; SQL — только чтение в repository,
   запись — в usecase; api не импортирует базу; внешние системы — за барьером
   clients; правила слоёв и grep-чеклист зафиксированы рядом с кодом.
9. **Состязательное ревью значимых изменений** (с этапа 10): независимые линзы
   ищут проблемы, верификаторы отбрасывают ложные; находки концентрируются на
   границах и гонках, которые «зелёные» тесты не ловят; каждая исправленная
   мутация покрыта тестом.
10. **Персонализация без изоляции** (с этапа 15): своё у каждого — эталоны,
    критерии, ключ ИИ, оценки; общее — структура, аналитики, документы и
    очередь. Разделение владения (чей объект) и полномочий (что можно) —
    разные оси, и лучше две колонки, чем одна роль-монолит.

## 20. Открытые темы (задел на продолжение книги)

Не реализовано и/или не решено на момент документа — потенциальные «следующие
этапы»:

- **Аудит действий:** события фоновых задач живут в памяти (пропадают при
  рестарте) и не образуют журнал «кто что запустил/изменил»; данные «Моей
  активности» берутся из того же летучего журнала. Постоянный журнал действий
  с атрибуцией — задел для ответов «кто это изменил».
- **Жизненный цикл сессий и пользователей:** сессии бессрочны до выхода;
  блокировка/удаление пользователя, сброс его личного доступа к ИИ из UI не
  предусмотрены (этап 15 закрыл вход, роли и права).
- **Автосинхронизация интервалом N** — есть планировщик, но бизнес-интервал не
  утверждён (БФТ №10).
- **Критерий принадлежности страниц:** сопоставление по email создателя;
  «создал vs редактировал» не разведено (БФТ №13).
- **Эволюция эталона:** история версий шаблона есть (каждое сохранение — новая
  версия, видна в UI, отчёты привязаны к версии), но отсутствуют откат к прежней
  версии и сравнение версий между собой; создание нового шаблона — только
  с нуля (клонировать существующий нельзя); повторяемые блоки доработок и поля
  name/description редактируются только в файле на сервере.
- **Подбор шаблона по типу документа:** в прогоне — включая массовую проверку
  всех документов аналитика — участвует один шаблон на все документы; для
  аналитика с документами разных типов массовый прогон всё ещё порождает шум
  ложных замечаний. Автоопределение типа по маркеру названия (маркер в эталоне
  уже есть) либо мультишаблонный прогон не реализованы.
- **Метрики эффекта:** средние оценки руководителя собираются и агрегируются
  с этапа 8; время ревью одного документа и доля проходящих проверку с первого
  раза — по-прежнему не собираются. Динамики оценок во времени нет: статистика
  фильтруется по периоду, но не строится как тренд.
- **Статистика в разрезе структуры:** оценки агрегируются по аналитику (этап 8);
  срезы «по команде» и «по кластеру» (этап 13) — средние баллы, доля проходящих
  проверку, состав доменов — не построены, хотя данные для них уже есть.
- **ИИ on-premise:** передача содержимого страниц внешнему API требует допуска ИБ
  (БФТ №9); настройка подключения из UI технически готова к смене эндпойнта.
- **Часовые пояса в UI:** бэкенд хранит и отдаёт время как наивный UTC;
  подзаголовок синхронизации (этап 10) дописывает суффикс Z и показывает
  локальное время пользователя, но остальные даты и времена интерфейса
  парсятся браузером как локальные — системного решения (зона в API либо
  единый фронтенд-хелпер) нет. Границы периода (этап 11) согласованы
  как UTC: date-only «с/по» парсится в полночь наивного UTC —
  пользователь в другой зоне получит сдвинутое окно.
- **Мобильные сценарии:** отдельной мобильной версии и целевого тестирования
  на мобильных нет; адаптивная вёрстка базовых экранов есть (десктоп — основной
  сценарий).
